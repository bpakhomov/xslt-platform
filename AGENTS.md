# Правила проекта

## Clean Code и Clean Architecture (Java 17/21+ / Spring Boot)

При написании нового и рефакторинге изменяемого Java-кода во всех сервисах (`xsltservice`, `xsltconverter`, `s3service`) соблюдай принципы Clean Code и Clean Architecture (Robert C. Martin):

### 1. Имена и читаемость
- **Классы и DTO:** существительные (`OrderProcessor`, `AuditService`, `CachedUser`).
- **Методы:** глаголы (`calculateDiscount`, `deactivateById`), булевы переменные и методы — предикаты (`isEligible`, `hasActiveSession`, `isActive`).
- **Запрещено:** сокращения, транслит, однобуквенные переменные (кроме `i`/`j` в тривиальных циклах и параметров коротких лямбд) и «магические» числа/строки (выноси в `Enum` или `private static final` константы).

### 2. Функции и методы
- **SLAP (Single Level of Abstraction Principle):** не смешивай в одном методе высокоуровневую бизнес-логику и низкоуровневые детали (SQL/HQL, маппинг, парсинг строк, сложные Stream API цепочки) — выноси детали в приватные методы или понятные локальные переменные.
- **Размер и фокус:** целевой размер метода — 5–15 строк, строго одна задача, без гигантских «master»-методов.
- **Количество аргументов:** 0–2 (3 в крайнем случае). Если больше — инкапсулируй в Parameter Object (`Java record`). *(Для Spring `@Autowired`-конструкторов допускается больше бинов, если зависимости логически не группируются.)*
- **Запрет на Flag Arguments:** не передавай `boolean` в метод для ветвления логики; создавай два отдельных метода с говорящими именами.
- **CQS (Command-Query Separation):** метод либо изменяет состояние (Command, возвращает `void` или результат мутации без скрытых чтений), либо возвращает данные без побочных эффектов (Query).

### 3. Комментарии
- **Запрещено:** очевидные комментарии, пояснения «что делает этот блок», Javadoc на геттерах/сеттерах и закомментированный мёртвый код. Если хочется написать комментарий — вынеси код в отдельный приватный метод с говорящим именем (комментируй только нетривиальное «почему»).

### 4. Объекты, данные и Modern Java
- **Data Structures vs Objects:** чётко разделяй иммутабельные `Java record` без бизнес-логики (для DTO, Value Object, Parameter Object) и обычные классы с инкапсулированным состоянием и поведением (включая JPA `@Entity` с учётом требований Hibernate).
- **Закон Деметры:** избегай цепочек вызовов вида `a.getB().getC().getD()`.
- **`null` и коллекции:** не возвращай и не передавай `null` во внутреннем коде; для штатного отсутствия значения используй `Optional<T>` только как возвращаемый тип, для пустых коллекций возвращай `List.of()` / `Set.of()`.

### 5. Обработка ошибок и классы
- **Исключения:** используй доменные unchecked-исключения вместо кодов возврата; выноси `try-catch` в отдельные небольшие приватные методы.
- **SRP и Stepdown Rule:** у класса одна причина для изменения. Публичные методы располагай вверху класса, вызываемые ими приватные методы — строго под ними в порядке вызова (уровнями абстракции сверху вниз).

## Unit-тесты (Java / JUnit 5 / Mockito)

При написании и рефакторинге unit-тестов во всех сервисах (`xsltservice`, `xsltconverter`, `s3service`) ориентируйся на `xsltservice/src/test/java/com/example/xsltservice/service/UserServiceTest.java` как на эталон и соблюдай принципы **F.I.R.S.T.**:

- **Given–When–Then (Arrange → Act → Assert):** один `@Test`-метод — один конкретный логический сценарий, без условных операторов (`if`/`switch`) и циклов внутри теста.
- **Инициализация (`@BeforeEach`):** создавай общие Mockito-моки и тестируемый экземпляр (SUT) в `@BeforeEach void setUp()`.
- **Структура (`@Nested`):** группируй тесты в `@Nested`-классы (1 уровень вложенности) по тестируемым методам, когда у метода несколько сценариев.
- **Граничные значения (`@ParameterizedTest`):** для проверки `null`, пустых и пробельных строк (`@NullAndEmptySource`, `@ValueSource`) и однотипных граничных кейсов используй `@ParameterizedTest` вместо дублирующих `@Test`.
- **Моки без `HttpServer`:** подменяй внешние зависимости, DAO и HTTP-клиенты (`HttpClient` и т.п.) через Mockito (`mock`, `when`, `verify`, `verifyNoInteractions`, `never`); не поднимай встроенный `HttpServer`, сокеты или Spring-контекст в unit-тестах.
- **Граница применимости:** правило относится к unit-тестам; интеграционные `@SpringBootTest`-тесты допустимы только там, где проверяется именно конфигурация/контекст Spring или интеграция слоёв.
